※ 농협 입사지원서 자기소개서 4개 문항 양식에 맞춰 작성했습니다. 양식 주의사항에 따라 본문에는 개인 식별정보(성명, 수험번호, 성별, 출신지역, 출신학교, 가족관계 등)를 기재하지 않았습니다.

01.직무 수행 시 핵심 역량 및 이를 갖추기 위한 노력646 / 700자

[규정을 코드로 옮기고 결과를 끝까지 검증하는 역량]

IT 직무에서 가장 중요한 역량은 업무 규정을 정확히 코드로 옮기고 그 결과 데이터를 끝까지 검증하는 능력이라고 생각합니다. 금리·수수료 계산이나 거래 처리처럼 금융 시스템은 계산 한 건의 오류도 고객 자산과 신뢰에 곧바로 영향을 주기 때문입니다.

이 역량을 갖추려고 규정 문서를 조문 단위로 분석해 코드로 구현하는 일부터 해 왔습니다. 전력거래소 기준서에 맞춰 한국과 일본 전력시장의 고객기준부하(CBL) 알고리즘 7종을 Python으로 구현하고 15분·30분·60분 주기의 시계열 데이터를 KDB+로 조회·가공했습니다. 계산 결과는 이상치 분석으로 다시 확인하며 정확도를 관리했고, 이후 이 시스템을 2년간 직접 운영했습니다.

규정을 옮기는 일과 함께 데이터를 모으고 저장하는 구조도 직접 설계했습니다. 분산 에너지 데이터 분석 플랫폼을 구축하며 API와 S3 등 여러 소스에서 1분 주기로 데이터를 모으는 파이프라인을 만들고 PostgreSQL 스키마 설계와 30여 개 REST API 개발을 맡았습니다. 배포는 GitHub Actions로 자동화해 개발·스테이징·운영 환경을 분리했습니다.

농협에서도 금융 업무 규정을 정확히 이해하고 그 결과를 검증할 수 있는 시스템으로 구현하겠습니다.

02.협업 과정에서 갈등을 해결한 경험과 그렇게 행동한 이유594 / 700자

[반복되는 머지 충돌을 팀의 규칙으로 줄이다]

첫 직장에서 여러 개발자가 한 저장소에서 함께 개발할 때, 코드를 병합하는 과정에서 충돌이 계속 발생했습니다. 브랜치를 나누고 합치는 기준이 정해져 있지 않다 보니 충돌을 해결하는 데 시간이 들었고 어떤 변경이 언제 운영에 반영됐는지 파악하기도 어려웠습니다.

저는 원인이 개인의 실수가 아니라 함께 지킬 규칙이 없다는 데 있다고 보았습니다. 그래서 먼저 브랜치 생성과 병합 기준을 정리한 Git 브랜치 관리 문서를 작성해 팀에 공유했습니다. 이어서 모든 변경은 PR을 거쳐 병합하도록 해 합치기 전에 변경 내용을 함께 확인하게 했습니다. 버전 관리 체계도 도입해 배포마다 릴리즈 노트를 작성했습니다.

그 결과 반복되던 머지 충돌이 크게 줄었습니다. 변경 사항은 병합 전에 PR에서 먼저 검토되었고, 배포된 버전마다 무엇이 바뀌었는지 릴리즈 노트로 추적할 수 있게 되었습니다. 이렇게 행동한 이유는 충돌이 덜 생기는 구조를 만드는 편이, 충돌이 날 때마다 누가 고칠지 따지는 것보다 팀 모두의 시간을 아끼는 길이기 때문입니다. 변경 이력 관리가 엄격한 금융 IT 환경이라면 협업의 기준부터 세우고 공유하겠습니다.

03.부정적 결과가 예상되는 상황에서도 도전했던 경험659 / 700자

[운영 중인 서버 구조를 바꾸기로 한 결정]

전력 수요반응 계산 시스템을 운영할 때, 동기식 Flask API 서버가 KDB+ 시계열 쿼리나 최적화 스케줄링 같은 무거운 연산을 처리하는 동안 서버 전체가 멈추고 다른 요청까지 밀리는 문제가 있었습니다. 연산이 특정 시간대에 몰리면 이런 지연이 반복됐습니다.

근본적인 해결책은 서버를 비동기 구조로 바꾸는 것이었지만 실제 서비스 중인 시스템의 뼈대를 바꾸는 일이라 전환 과정에서 장애가 생길 위험이 있었습니다. 그러나 그대로 두면 연산이 몰릴 때마다 같은 문제가 되풀이될 것이 분명했습니다.

저는 구조를 바꾸되 위험은 줄이는 방법을 택했습니다. Uvicorn 기반 FastAPI 비동기 서버로 마이그레이션하고 부하가 큰 연산은 Gevent 기반 분산 태스크 워커 8개로 분리해 요청 처리와 떼어 놓았습니다. 변경 사항은 개발·스테이징·운영으로 분리된 배포 파이프라인을 거치며 운영에 반영하기 전에 먼저 확인했습니다.

전환 뒤에는 연산이 몰리는 시간대에도 서버가 멈추지 않고 안정적인 응답 속도를 유지했습니다. 원인을 정확히 짚고 안전장치를 갖춘 채 구조를 고치면, 위험을 이유로 미룰 때보다 장기적으로 더 안전하다는 것을 이 일로 알게 되었습니다. 중단 없는 서비스가 중요한 금융 시스템을 다룰 때 이 원칙을 지키겠습니다.

04.사용자(상대방)의 관점에서 생각하고 행동했던 경험607 / 700자

[운영자가 바로 판단할 수 있는 화면을 만들다]

전기차 충전소 관리 시스템을 개발할 때 화면의 사용자는 충전소 운영 담당자였습니다. 이들이 확인해야 할 정보는 충전 중인 차량, ESS 상태, 이동형 배터리(MBESS)의 충·방전량과 배터리 수명, 배터리 내부 셀 데이터까지 다양했습니다.

개발자 입장에서는 데이터를 빠짐없이 보여주면 충분해 보였지만 운영자에게는 지금 어디에 문제가 있는지 빠르게 판단하는 일이 필요했습니다. 그래서 충전량·방전량·SOC 등 여러 지표를 하나의 통합 대시보드에 배치해 충전소 상태를 한눈에 파악하도록 하고 셀 단위 데이터는 상세 화면으로 분리했습니다. 배터리 시스템에 이상이 감지되면 알림창으로 즉시 알리도록 했습니다.

이후 VPP 플랫폼에서도 같은 원칙으로 모니터링 화면과 시스템 전체 알림 UI를 개발했습니다. 모니터링 화면에서는 여러 참여자를 묶은 Balancing Group이 지령을 수행하는지 실시간으로 확인하도록 했습니다. 데이터를 많이 보여주는 것보다 사용자가 다음 행동을 바로 정할 수 있게 돕는 것이 좋은 화면이라는 점을 배웠습니다. 농협에서도 영업점 직원과 고객이 화면을 보고 바로 판단할 수 있도록 사용자 입장에서 설계하겠습니다.
